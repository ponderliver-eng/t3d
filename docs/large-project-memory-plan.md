# T3D 大体积与大量资产导入：内存与显存方案

目标只有一个：**导入很大的资源包，或者一次导入很多资产时，编辑器不崩、显存不爆、画面不出错。**

做法归结为三句话：

1. **导入不加载**：导入只负责把文件写进工程、出缩略图、烘好成品，不把资源留在内存和显存里。
2. **加载只按引用**：只有当前场景用到的资源才留在内存里，用不到的自动释放，再用时从成品读回。
3. **超预算就降级**：显存估算超出预算时，先释放、再降清晰度，而不是继续加载直到崩溃。

状态标记：✅ 已实现　⏳ 后续　❌ 明确不做

---

## 一、原来会在哪里崩

| 位置 | 原因 |
| --- | --- |
| 打开资源包 | 渲染进程把整个 `.unitypackage` 读进内存再整体解压，包超过约 2GB 就超出单块内存上限 |
| 扫描资源包 | 每个条目的文件内容都留在内存里，直到对话框关闭 |
| 导入入库 | 每导入一张贴图、一个模型就立刻加载进显存且不释放，几百个文件后显存耗尽 |
| 切换场景 | 上一个场景的贴图和模型一直留着；删除资源时模型的几何体和材质也没有真正释放 |
| 坏文件 | 加载失败的资源每次渲染都重试，既卡又不提示 |

原方案里有两点不准确，这里更正：

- 贴图最大尺寸 2048 的限制原本就有（`MAX_TEXTURE_SIZE`），不需要新增。
- 贴图并非「只进不出」，删除资源时会释放；真正漏的是模型，以及切换场景后不回收。

## 二、已实现的部分

### 2.1 资源包流式解包 ✅

- 主进程边解压边写临时文件（系统临时目录下的 `T3D-pkg-staging/<会话>.tar`），同时建立索引，只记每个条目的路径、位置和大小。实现在 `electron/services/packageArchive.ts`。
- 渲染进程通过 `package:open` / `package:read` / `package:close` 按位置一次读一个条目。扫描时只读路径、`.meta`、材质和预制体这类小文本；模型、贴图、音频本体要到真正导入那一条时才读。
- 开始前检查磁盘剩余空间（至少为压缩包的 1.5 倍）；包被截断时明确报「资源包不完整」。
- 临时文件在关闭对话框、退出编辑器、下次启动时都会清理。
- 本地路径只在 preload 里获取，不交给网页内容；主进程只接受 `.unitypackage`。
- 网页版没有主进程，超过 1GB 的包直接提示改用桌面版。

### 2.2 批量导入只落盘 ✅

一次导入**超过 12 个文件或超过 256MB** 时自动进入批量模式（`src/editor/assets/import.ts`）：

- 贴图：解码一次，压成 BC7 成品写盘，随即释放，不进显存。
- 模型：逐个处理，成品写完后立刻释放；资源包里自带的预览图直接当缩略图用，不再逐个渲染。
- 同时解码的原图最多 3 张。
- 文件没能写进工程的资源不会释放内存副本，避免丢数据。
- 提取过程可以取消；已导入的保留，重新导入时相同内容按哈希去重，不会重复入库。
- 失败的条目逐条写进日志（最多列 20 条）。

小于这个门槛的导入走原来的流程，行为不变。

### 2.3 按引用回收 ✅

`src/editor/assets/assetMemory.ts` 负责释放当前场景没用到的贴图和模型。「用到」的判定宁多勿漏：除了场景节点、环境贴图以及它们引用的材质、特效、界面，还会把节点和画面设置里的全部内容（玩法数据、能力包参数、着色器参数）扫一遍，凡是出现的资源编号都算引用，并沿着材质、预制体、模型自动绑定的材质槽继续展开；正在资源检视面板里看的资源及其贴图也保留。已加载的动作资源不回收（常按片段名引用，且不带网格和贴图）。

触发时机：

- 切换场景 4 秒后
- 显存估算超出预算时
- 批量导入结束时
- 文件菜单「释放未引用资源」

不回收的情况：试玩期间；正在加载的资源；有尚未保存的内存改动的模型（例如刚并入了重定向动画）。

释放模型时会连同几何体、材质和模型文件里内嵌的贴图一起释放。

### 2.4 显存预算与降级 ✅

- 预算默认 3072MB，可通过 `localStorage` 的 `t3d.memory.textureBudgetMb` 调整。
- 超预算时先回收未引用资源；仍然超出，则新加载的 BC7 贴图跳过最高的 1 到 2 级清晰度（长边不低于 256），并在日志里提示，每分钟最多一次。
- 占用回落到预算的 85% 以下后，被降级的贴图恢复原清晰度。已知限制：恢复是先释放再重新加载，那张贴图会有一瞬间不显示。

注意：这里的占用是**按贴图尺寸和格式估算的**，不是显卡的真实读数。浏览器不提供真实显存用量。

### 2.5 加载失败可见 ✅

`src/editor/assets/loadFailures.ts`：同一资源加载失败后隔 2 秒、8 秒各重试一次，3 次都失败就停止自动重试，并在日志里报一次。用户主动重新加载不受限制。

### 2.6 发布端（Player）资源与显存 ✅

- **切换场景回收**：新场景挂载完成后，释放上一场景不再引用的模型、贴图与环境贴图，并释放旧场景网格克隆出来的材质；加载界面用到的背景图和图标会保留。
- **按需加载与后台预热门槛**：可加载资源超过 48 个时不再在后台把其余场景全预热进内存，留到切场景时再加载；`minimal` 预加载模式和脚本运行期刷出的预制体会在第一次访问模型或贴图时按需加载，并在加载完成后补挂到场景上。
- **桌面端带上 BC7 成品**：构建桌面端时，贴图除了保留 PNG / WebP（供加载界面封面、图标和不支持 BC7 的显卡回退）外，还会把缓存里的 BC7 成品一起导出（文件名是原文件名加后缀，如 `a.png.bc7`、`a.png.unity-mr.bc7`；缓存里没有时用工程里的原始文件当场烘焙），并按构建设置的尺寸上限裁掉最高级清晰度；Player 在支持 BC7 的显卡上直接上传压缩块，贴图显存降为四分之一。代价是包体变大（一张 2048 贴图约多 5.6MB），可在构建设置里关掉「桌面端附带 BC7 压缩贴图」（`BuildSettings.desktopBc7Textures`，默认开）。
- **加载失败提示**：资源加载失败不再只打控制台警告，画面左下角会弹出提示条，并且同一资源失败后不再反复请求；切换场景时清掉失败记录，再给一次重试机会。提示条默认不显示（玩家看不到，失败只写控制台），需要排查时在构建设置里勾上「画面上提示资源加载失败」（`BuildSettings.showLoadFailures`）。
- **排查入口**：控制台执行 `__T3D_ASSET_STATS__()` 可以看到当前留在内存里的贴图 / 模型数量、压缩贴图数量、贴图显存估算和失败列表。

### 2.7 验证情况

- 自动测试：`npm run test:assets`，覆盖索引器、会话的解压读取清理、扫描器不读大文件、预算计算、失败重试、BC7 成品打包与尺寸裁剪；`npm run check:player-deps` 与 `npm run build:player` 通过。
- 实机检查（桌面版，独立用户目录）：导入一个含 40 张贴图、2 个模型、1 个材质的资源包，结果是全部入库且都有缩略图，导入后内存里没有留下贴图和模型，临时文件已清理；随后首次使用时贴图直接读到 BC7 成品、模型读到 GLB 成品，回收后归零；单张贴图的普通导入仍留在内存中可直接使用。
- Player 实机检查（真实 Electron + WebGPU 跑 `dist-player/`，喂一个手工合成的两场景导出包）：BC7 成品被实际用于渲染（成品与原图故意做成不同颜色来区分）；不在预加载清单里的贴图和模型按需加载后补挂到场景上；切场景后上一场景的贴图和模型数量归零、只请求新场景的文件；来回切换 8 次资源数量不增长；资源超过 48 个时没有后台预热；缺失的贴图弹出提示条，每次进场景只尝试加载一轮，不会每帧反复请求。
- **尚未验证**：GB 级的真实资源包、显存真的逼近预算时的降级效果、从编辑器「构建」按钮走完整导出流程产出的桌面包（导出器写 BC7 文件这一步只过了类型检查）、Unity 金属度贴图的 BC7 重排成品在 Player 里的效果、编辑器里扩大后的引用判定在真实大工程上的表现。

## 三、对普通资源的影响

不变的：

- 12 个文件以内且不超过 256MB 的导入流程。
- 成品缓存的格式和位置，已有工程不需要重建缓存。
- 打开工程时的预热。
- 显存估算在预算内时，贴图的加载结果和清晰度。

有变化的：

- 切换场景后，新场景没用到的资源会被释放；切回去时从成品重新读，会有一次短暂加载。
- 批量导入的资源第一次使用时才加载。
- 首次加载大量还没有成品的贴图会稍慢（同时解码最多 3 张），但内存不会冲高。
- 坏文件失败 3 次后不再反复重试。

## 四、明确不做的

| 项目 | 原因 |
| --- | --- |
| `--max-old-space-size=8192` | Electron 的 JS 堆上限固定在 4GB 左右，这个参数调不上去；而且导入时撑爆的是文件字节，不在这个堆里 |
| 上传显卡后释放内存里的像素副本 | 回收之后、设备重建之后都需要重新上传，没有副本就得重新读盘解码；BC7 副本本身只有原图的四分之一 |
| 把贴图尺寸对齐到 4 的倍数以便都能压 BC7 | 需要重采样，会让像素图和界面图变糊；这类贴图保持不压缩 |
| 导入前置设置面板 | 批量模式按数量和体积自动判断，不需要用户做选择；贴图上限 2048 已是固定行为 |
| 导入清单与断点续传 | 相同内容按哈希去重，重新导入一遍结果相同，不需要另外维护清单 |
| 模型解析放到后台线程 | 改动大，而批量模式下逐个处理已经把内存压住 |
| 显卡设备丢失后自动恢复 | 属于渲染器层面的独立问题，不在本方案范围 |

- ⏳ **资源面板虚拟滚动**：资源上千后只渲染可见的卡片。
- ⏳ **缩略图外置**：从工程文件里移到缓存目录，避免工程文件随资源数量膨胀。

- ⏳ **引用查询**：查看资源被哪些场景、节点、材质引用，删除前预警。
- ⏳ **大地图储备**：场景分文件存储、分块加载、自动简化模型、重复物体自动合批。等有实际的大地图需求再做。
