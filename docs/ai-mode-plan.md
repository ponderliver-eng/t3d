# AI 驱动的游戏工程管理器与能力沉淀：总体规划

本文是 T3D 演进为「以 AI 生产为核心的游戏工程管理器」的总体规划，供后续分阶段开发使用。它和 `editor-phase-plan.md` 的关系：阶段 9（脚手架、Web 导出）被并入本文的阶段 2 和阶段 4；后续不再投入重型手配工作台，新增能力全面转向服务 AI 生产与工程管理。

本文写于 2026-11，依据当时的代码现状。关键设计决策在第 12 节汇总，阶段 0 先完成接口契约与规则修订。

---

## 1. 定位

**生产过程以 AI 为核心；T3D 本质上是「AI 驱动的游戏工程管理器」，承担六大工程管理职能（立项与设计中枢、资源/数据与包管理、实时试玩台、调试/体检与性能守门、版本快照与实验对比、验证发布与能力沉淀），手动编辑退居为局部微调的辅助手段。**

| 角色 | 职责 |
|---|---|
| **AI（生产主力）** | 理解需求并维护全局设计规范（`design.md`）、拆解计划、调用 T3D 能力搭建多关卡场景、编写脚本与着色器、组装界面与配置策划数值表、调用生成服务产出素材、跑试玩探针自检并修复问题、把成果沉淀成可复用的能力包 |
| **T3D（工程管理器与底座）** | 提供确定性的运行时与渲染管线、结构化的工程文件树与设计记忆管理、资产入库自动规整与外部工具链桥接、多端输入映射与实时试玩台、调试体检与性能预算守门、版本快照与分支对比、一键导出发布，以及供人随手微调的参数面板与 Gizmo |
| **人（导演与验收者）** | 定方向与审美规范、在视口里指点要改的对象、试玩体验、看调试/性能与验证报告、用滑条/手柄或外部软件做局部微调、管理版本快照与能力包、确认发布 |
| **产物** | 结构清晰的游戏工程文件夹、经过试玩验证与性能守门的播放包，以及从工程里沉淀出来、下次可直接复用的能力包 |

四条贯穿始终的原则：

1. **AI 生产为主，手动为辅。** 不再新建复杂的手配低代码工作台或连线图编辑器；所有新增能力只需要提供：`FieldSchema`（自动生成参数面板）+ 指令/API + 运行时逻辑。
2. **工程即清晰的文件树。** 场景、预制体、界面、材质、数据表、脚本、着色器各自是工程文件夹下的独立小文件，便于 AI 局部读写、便于快照对比、便于直接打包沉淀。
3. **人和 AI 走同一条指令层。** AI 调工具与人拖滑条/移动手柄走同一套指令与校验；人在视口里的任何点选、圈选、微调都能直接成为下一轮 AI 的上下文。
4. **每一步可调试、可回滚、可沉淀。** 每轮 AI 生产自动生成工程快照（Checkpoint），配齐体检与试玩探针报告；做成的模块随时可提取成能力包。

## 2. 现状

### 2.1 已经具备

- **工程是纯数据。** 场景节点、画面、能力包数据（`node.capabilities` / `picture.capabilities`）、玩法数据（`node.gameplay`）、律令、游戏数据表、界面文档（带 `schemaVersion`）都可序列化。
- **扩展走登记制。** `src/capabilities/registry.ts` 的 `CapabilityManifest`，`src/gameplay/registry.ts` 的 `GameplayPackManifest`（表、组件、触发、条件、动作）。关闭后数据保留，律令标缺失。
- **统一运行时调度。** `stepSceneRuntime` + `SceneRuntimeHost` + `RUNTIME_STAGE`，试玩和将来的导出共用。
- **资产管线成熟。** 内容寻址、导入产物缓存、材质自动匹配、缩略图、懒加载。
- **有引用检查和无界面测试的雏形。** `src/gameplay/common/referenceIssues.ts`，`tests/gameplay-*.test.mjs`。

### 2.2 缺口

| # | 缺口 | 现状依据 |
|---|---|---|
| 1 | 没有统一的调用入口 | `store.ts` 约 90 个动作，文档修改与界面状态混在一起；不少修改逻辑写在卡片组件里；失败没有结构化返回 |
| 2 | 清单不是机器可读的 | 组件只有 `defaultData` 和 React 卡片；字段类型与范围藏在各个 `normalize*` 函数里 |
| 3 | 运行时没有和编辑器分开 | `src/runtime` 下多个文件直接引用编辑器 store；律令卡片等界面文件也放在 `runtime` 目录 |
| 4 | 没有导出 | 代码里没有播放包入口；`vite build` 打的是编辑器 |
| 5 | 没有脚手架 | 阶段 9 的三个脚手架未实现 |
| 6 | 脚本和自定义着色器不是资产 | 资产种类里没有这两项；现行规则只允许「脚本作为律令里的一步」；材质只能在 5 个固定着色器里选 |
| 6a | 部分资源不适合 AI 生成 | 特效的 `simulation` 没有类型；没有应用内的编译检查和离屏预览（详见第 9 节） |
| 7 | 包只能写在源码里 | 两个登记表都是编译期常量；没有安装、卸载、版本 |
| 8 | 没有异步任务和密钥管理 | Electron 主进程只有文件接口，且接受任意路径 |
| 9 | 试玩不可观测 | 没有虚拟输入、定步长推进、状态断言、截图接口 |
| 10 | 撤销是整份快照 | `HistoryEntry` 记前后全量节点；多种修改类型各有一套字段，没有通用的「一批操作合一步」 |

## 3. 目标架构与工程文件结构

### 3.1 系统分层

```
┌──────────────────────────────────────────────────────────┐
│ 工作台界面   AI 创作主视图 │ 资源与包管理 │ 试玩调试 │ 发布 │
│             （手动检查器与 Gizmo 作为辅助抽屉/覆盖层按需展开）│
├──────────────────────────────────────────────────────────┤
│ 内置 Agent   对话 · 计划 · 进度 · 视口上下文 · 模型接入适配  │
│             （可接各家模型 API，不持有工程状态）             │
├──────────────────────────────────────────────────────────┤
│ 工具面       进程内的工具表：查询 / 指令 / 体检 / 试玩 /     │
│             生成 / 导出 / 沉淀                              │
├──────────────────────────────────────────────────────────┤
│ 指令层       指令总线 · 参数说明 · 校验 · 快照与撤销 · 权限   │
├──────────────────────────────────────────────────────────┤
│ T3D 内核     工程文件系统 · 登记表（官方包 + 已安装的包）·   │
│             运行时 · 资产管线 · 试玩探针 · 导出 · 包管理     │
└──────────────────────────────────────────────────────────┘
```

内核不认识 AI。指令层以上的每一层都可以单独替换，工程照常加载、试玩与导出。

Agent 是 T3D 自带的，不依赖外部 Agent 工具，也不走 MCP。工具面就是进程内的一张工具表，Agent 直接调用。

### 3.2 拆分后的工程文件夹结构

既然生产以 AI 为主、编辑器是工程管理器，就不再把所有数据塞进一个巨型 JSON，而是**按职责拆成干净的文本文件树**（AI 按需读写单文件、极省上下文、天然支持快照对比与能力沉淀）：

```
<工程目录>/
  project.json             工程清单、开启的能力与包、全局画面配置、入口场景与关卡流转、性能预算阈值
  design.md                游戏设计概要与风格规范（核心循环、美术风格词、镜头视角、色彩板、命名约定，作为 AI 常驻记忆）
  input.json               语义化动作输入映射表（Action Map：如 Jump/Fire/Move 绑定键鼠、手柄、触屏虚拟摇杆）
  scenes/
    main.scene.json        单场景节点树与场景级能力数据
  prefabs/
    enemy.prefab.json      预制体定义
  ui/
    hud.ui.json            界面文档
  materials/
    lava.mat.json          材质（引用的着色器 ID + 参数值）
  tables/
    units.table.json       游戏数据表定义与策划数值行
  scripts/
    patrol.ts              行为脚本与运行时系统脚本
  shaders/
    lava.shader.ts         TSL 表面着色器
  assets/                  模型、贴图、音频、动画等二进制资产与自动规整后的导入缓存
  packs/                   本工程安装的包副本
  .t3d/
    runtime.d.ts           自动生成的运行时类型定义（供 AI 与外部编辑器补全）
    shader.d.ts            自动生成的着色器类型定义
    checkpoints/           每轮 AI 生产自动保存的轻量工程快照、里程碑星标与实验分支
    chat-history.json      对话、计划与操作日志
  tsconfig.json
```

### 3.3 源码目录落点（新增，不动现有目录的职责）

- `src/core/commands/`：指令总线、指令定义、事务与工程快照
- `src/core/schema/`：字段说明的声明式定义、校验与自动属性面板
- `src/core/query/`：工程摘要、按需查询、体检
- `src/core/codeAssets/`：着色器与脚本的编译、检查、诊断、热重载
- `src/core/preview/`：离屏预览（复用主渲染器）
- `src/player/`：播放包入口与宿主
- `src/playtest/`：试玩探针
- `src/packs/`：包格式、安装、沉淀
- `src/ai/`：Agent 循环、工具面、AI 工作台界面、配方执行
- `electron/services/`：模型接入适配、任务队列、密钥、生成服务适配

## 4. 指令层

### 4.1 指令

每条指令是一份声明加一个执行函数。界面和 AI 都只通过 `dispatch` 改工程。

```ts
interface CommandDef<P, R> {
  id: string                       // 'scene.createNode'
  title: string                    // 给人和 AI 看的一句话说明
  params: FieldSchema              // 参数说明，见 4.2
  risk: 'safe' | 'confirm'         // 删除、覆盖、花钱、导出为 confirm
  run: (ctx: CommandContext, params: P) => CommandResult<R>
}

type CommandResult<R> =
  | { ok: true, value: R, changed: ChangeSummary }
  | { ok: false, code: string, message: string, hint?: string }
```

要求：

- **失败必须说清楚原因和下一步。** 例如：`{ code: 'capability.unsupportedKind', message: '点光源不能挂水体', hint: '可用的节点种类：空物体、平面、模型' }`。AI 靠这个自我纠正。
- **粒度按意图，不按字段。** 「挂水体并套用海洋预设」是一条。另留一条通用的 `doc.setValue(path, value)` 兜底，同样经过校验。
- **支持辅助放置。** `scene` 域的创建与变换指令支持「贴地放置」「对齐到目标物体表面」等参数，避免 AI 盲算三维坐标导致浮空或穿模。
- **试玩期间拒绝文档修改指令。** `playState === 'playing'` 时调用修改工程的指令直接返回错误（或先调用停止试玩），不触碰「试玩时不改 store」的红线。
- **不在指令里做界面的事。** 选中、聚焦、面板开关这类保留在 store，不进指令层。

指令域（阶段 1 先做前 7 个，其余随对应阶段补齐）：

| 域 | 示例 |
|---|---|
| `scene` | 创建、删除、复制、改父子、改变换（含贴地/对齐）、改属性、实例化预制体 |
| `capability` | 开关工程能力、给节点挂/改/卸能力数据、改场景级能力数据 |
| `gameplay` | 开关玩法包、挂/改组件、增删改数据表行 |
| `ui` | 新建界面文档、整树替换、局部修改、挂到场景 |
| `asset` | 导入、移动、重命名、删除、新建材质/预制体 |
| `picture` | 画面与后期参数 |
| `project` | 保存、读写 `design.md` 设计规范与 `input.json` 输入映射、新建/切换场景、设置关卡流转与性能预算 |
| `shader` | 新建、修改、检查着色器资产（阶段 3） |
| `script` | 新建、修改、检查脚本资产，挂到节点并填参数（阶段 3） |
| `effect` | 套用特效预设并改参数（阶段 3） |
| `pack` | 安装、卸载、导出、沉淀为包（阶段 4） |

说明：律令（`rules`）是面向开发模式的手配低代码模块，不进 AI 工具面（见 9.4）。

### 4.2 字段说明

把现在散在 `normalize*` 里的隐含规则改成声明，三处共用：校验与规范化、属性面板控件的范围、AI 工具说明。

```ts
type FieldSchema =
  | { type: 'number', min?: number, max?: number, step?: number, default: number, label: string, unit?: string }
  | { type: 'boolean' | 'string' | 'color', default: unknown, label: string }
  | { type: 'vec2' | 'vec3' | 'vec4', default: number[], label: string }
  | { type: 'enum', options: Array<{ value: string, label: string }>, default: string, label: string }
  | { type: 'texture', default?: string, label: string }                             // 贴图资产引用的简写
  | { type: 'ref', target: 'asset' | 'node' | 'tableRow' | 'clip', kinds?: string[], tableId?: string, label: string }
  | { type: 'object', fields: Record<string, FieldSchema>, label?: string }
  | { type: 'list', item: FieldSchema, label: string }
```

- 能力包的 `defaults.ts` 逐步改成导出一份 `FieldSchema`，`normalize*` 由它生成。
- `GameplayPackManifest` 的组件各补一份 `FieldSchema`。
- 有了字段说明，**没有手写卡片的组件、着色器参数、脚本参数都可以自动生成属性卡片**。这是后面「用户包不带 React 代码」的前提（见第 10 节），也是统一参数说明的底座（见 9.7）。

### 4.3 事务、撤销与版本快照树（Checkpoint & Branch）

- `beginTransaction(label)` / `commitTransaction()` / `rollbackTransaction()`。事务内的所有指令合成一步撤销。
- AI 的一轮执行默认是一个事务；计划里的每一步是子事务，可以单步回滚。
- **版本快照与实验分支（Checkpoint & Branch）**：除了内存里的 `Ctrl+Z` 变更集撤销，每轮 AI 任务开始前自动在 `.t3d/checkpoints/` 记录一次轻量文件快照（基于文件哈希，只存改动过的小文件）。支持：
  - 给关键节点打**里程碑星标**（如 `v0.1 核心移动跑通`、`v0.2 加上 Boss 战`）；
  - 从任意快照拉出**轻量实验分支**（让 AI 尝试另一套关卡布局或手感方案，两边直接切换试玩对比，选定后再设为主线）。
- **跨磁盘文件的回滚：** 着色器、脚本及拆分后的工程文件都在事务保护范围内，回滚或切换快照分支时磁盘文件同步恢复。

### 4.4 权限

- 文件访问限定在工程目录和用户库目录内。现有的 `fs:*` 接口接受任意路径，接入 AI 前必须加路径校验。
- `risk: 'confirm'` 的指令在 AI 调用时弹确认：删除资产、覆盖已有内容、产生费用的生成、导出、安装含脚本的包。
- 每次 AI 调用记入操作日志（指令、参数、结果、耗时），面板里可查。

## 5. 查询与体检

### 5.1 查询

AI 默认只拿摘要，细节按需取，不把整份场景放进上下文。

| 工具 | 返回 |
|---|---|
| `project.overview` | `design.md` 设计规范摘要、输入映射、场景与关卡流转图、已开的能力与玩法包、节点数量与大纲（前两层）、资产统计、当前性能预算占用 |
| `scene.outline(parentId?, depth?)` | 指定范围的层级 |
| `node.inspect(id)` | 单节点完整数据（按挂载槽分组），以及世界包围盒尺寸、底部高度、朝向 |
| `asset.search(query, kind?)` | 名称、标签、种类匹配的资产；模型类资产同时返回包围盒尺寸、原点偏移、默认朝向、面数与贴图分辨率 |
| `registry.describe(kind, id?)` | 能力、玩法包、组件、脚本、着色器、指令的说明与 `FieldSchema` |
| `db.rows(tableId, filter?)` | 数据表行与被引用统计 |

### 5.2 体检与性能预算守门

`project.diagnose()` 返回一份问题清单，每条带级别、位置和修复建议。

- **引用**：丢失的资产、节点、数据行、片段（扩展 `referenceIssues.ts`）。
- **可玩性**：没有主角或出生点、没有相机、没有光、主角脚下没有碰撞、导航网格没烘焙、关卡流转存在死路、律令引用了已关闭的包。
- **界面**：绑定的变量不存在、按钮没有点击动作、在目标分辨率下控件越界重叠。
- **资产规范与性能预算（Asset Gatekeeper & Budget）**：单模型面数超标、原点未对齐底部、尺寸比例异常、未压缩的大贴图、场景总面数 / DrawCall / 显存 / 预计包体大小超出 `project.json` 设定的预算阈值。
- **包**：依赖没装、版本不匹配、脚本或着色器编译失败。

体检是导出和沉淀的前置条件：有错误级问题时两者都拒绝执行。

## 6. 运行时独立与导出

### 6.1 解耦

目标：`src/runtime`、`src/capabilities/*/session.ts`、`src/gameplay/*/runtime.ts` 不再引用 `useEditorStore` 和 `src/editor/panels`。

- 定义 `RuntimeWorld` 接口：读节点文档、读游戏数据、读写运行时变量、发消息、写日志。编辑器用 store 实现它，播放包用只读的工程数据实现它。
- 界面文件（`RulesCard.tsx`、`CharacterCard.tsx`、`DeviceCards.tsx`、`RulesWorkbench.tsx` 等）从 `src/runtime` 移到 `src/editor/gameplay/`。
- 加一条构建检查：播放包入口的依赖图里出现 `src/editor/` 即失败。

### 6.2 播放包

- `src/player/main.ts`：创建同一个 `WebGPURenderer`（带 WebGL2 回退），实现 `SceneRuntimeHost`，加载工程数据，跑 `stepSceneRuntime`。
- 导出流程：收集引用到的资产 → 只带已开启且被用到的能力与玩法包 → 写出静态目录。
- 不含编辑器外壳、界面编辑器、撤销历史、辅助图形。
- 导出前强制体检；阶段 2 试玩探针就绪后一并跑冒烟试玩。

桌面安装包是否纳入，见第 12 节。

## 7. 试玩探针

让程序（测试脚本或 AI）能跑游戏并看到结果。

```ts
interface PlaytestSession {
  start(sceneId?: string): Promise<void>
  step(seconds: number): Promise<void>            // 定步长推进，不依赖真实时间
  input(events: InputEvent[]): void               // 按键、鼠标、点击界面控件
  read(query: StateQuery): unknown                // 变量、节点位置、标签、组件字段
  waitFor(cond: Condition, timeout: number): Promise<boolean>
  capture(camera?: CameraPreset): Promise<ImageRef>
  report(): PlaytestReport                        // 错误、警告、帧耗时、绘制调用
  stop(): Promise<void>
}
```

- 定步长推进要求运行时不直接读系统时间，统一从 `dt` 累计。
- 截图用于 AI 的视觉自检（黑屏、穿模、界面重叠），也存进验证报告。
- **冒烟脚本**是一种资产：一串输入加断言。每个配方自带一份；AI 生成游戏后会补一份。
- 试玩探针同时用于自动化回归测试，不只服务 AI。

## 8. AI 层与工程管理器界面

### 8.1 工作台定位：AI 生产为主，六大工程管理支柱 + 手动辅助

T3D 不再把「传统重型手配编辑器」和「AI 模式」当成平起平坐的两套世界，而是**以 AI 为核心生产方式，工具自身围绕完整的游戏工程生命周期提供「六大工程管理支柱」，手动编辑作为按需展开的辅助手段**。

| 工程管理支柱 | 管什么 | 人与工具的协同方式 |
|---|---|---|
| **AI 生产指挥台（常驻核心）** | 需求对话、计划拆解、结构化执行流、内联微调、产出清单 | 人提需求与验收；AI 拆计划并调指令生产 |
| **1. 立项与设计中枢（Blueprint & Memory）** | `design.md`（玩法循环、美术风格词、镜头、色彩板、命名约定）与**多场景关卡流转图（Scene Flow）** | 立项时 AI 与人共同生成并维护，后续写脚本、调材质、生成美术素材全部自动遵循该规范；在关卡流转图上一键跳关试玩 |
| **2. 资源、策划表与包管理（Assets, Tables & Packs）** | 资产库、**导入自动规整管线**（居中底部原点、统一米制尺寸、自动减面/压缩贴图、生成碰撞体）、**外部工具链桥接**（一键用 Cursor/Blender/PS 打开，保存即热重载）、策划数值表与难度曲线、能力包安装与用户库 | 告别因 AI 生模型尺寸/面数失控导致的穿模卡死；策划表支持直观浏览与让 AI 批量平衡数值；外部专业软件无缝接入 |
| **3. 实时试玩台（Playtest Stage）** | 实时 3D/UI 主视口、`input.json` **语义化动作输入映射**（键鼠/手柄/触屏摇杆统一映射）、**多端屏幕比例切换**（16:9 桌面 / 9:16 竖屏 / 16:9 移动触控）、倍速与单步控制 | 亲自试玩手感，随时切分辨率检查 UI 适配，触发自动化冒烟脚本 |
| **4. 调试、体检与性能守门（Debug & Budget）** | 运行时状态监视（变量、节点状态、单脚本耗时）、完整性体检、**常驻性能预算看板**（总面数、DrawCall、显存、包体大小阈值守门） | 哪项指标超标或报错自动标红，点「交给 AI 修 / 优化」直接把诊断和超标资产送入对话处理 |
| **5. 版本快照与实验对比（Snapshots & Branch）** | 每轮自动快照（Checkpoint）、里程碑星标版本、**轻量实验分支（A/B 方案试玩对比）** | 改坏了一键回退；想试两种关卡布局或两套打击感时拉分支对比试玩，选好后设为主线 |
| **6. 验证发布与能力沉淀（Release & Distill）** | 导出前强制体检 + 冒烟验证、随包产出验证报告、Web 播放包构建、一键提取能力包入库 | 审阅报告后一键导出可分发的 Web 游戏，或把本工程的脚本/着色器/预制体沉淀成包供下个项目复用 |
| **手动辅助（按需抽屉）** | 场景层级树、选中对象的自动参数面板、视口移动/旋转/缩放手柄、轻量代码框 | 随手挪一下位置、拖滑条微调数值、换张贴图 |

核心交互——**「指哪打哪」的视口上下文传递**：

- **点选 / 圈选即上下文**：人在视口或界面预览里点选一个或多个物体（或拉框圈中一片区域），直接输入「把这几棵树散开一点」「给这个怪加个受击闪白」，系统自动把选中节点的 ID、坐标、包围盒、挂载脚本和材质附带进本轮请求。
- **截图圈注（Visual Markup）**：试玩暂停或预览时，可在视口画面上随手画圈或箭头并附一句话，连同画面截图、当前相机参数和可见节点列表一起发给 AI。
- **报错一键交办**：体检列表、控制台报错、试玩探针失败项旁都有「交给 AI 修」，点一下就把结构化诊断和相关文件路径直接送入对话。
- **人手微调与 AI 无缝衔接**：人在辅助面板里拖了滑条、挪了物体，或用外部编辑器改了 `.ts` 文件，AI 下一轮通过查询工具直接读取最新文件与状态，不依赖旧记忆。

说明：`editor-phase-plan.md` 的「第一版明确不做」里有「创作模式与高级模式的切换」。那一条针对的是用原子积木拼游戏的简化模式；本架构不引入积木系统，手动辅助与 AI 操作的是同一套工程文件。阶段 0 修订该条的表述。

### 8.1a 界面与交互体验规范（专业、克制、零割裂）

AI 工作台**绝不能做成「普通网页聊天框贴在编辑器旁边」**，必须像专业 DCC / 现代 IDE 一样高密度、响应迅速、视口与对话深度联动：

1. **三区黄金布局（视口永远是中心）**
   ```
   ┌─────────────────────────────────────────────────────────────────────────┐
   │ 顶栏：工程名 │ [立项/蓝图] [创作/试玩] [资源/表/包] [调试/预算] [发布] │ 快照·试玩▶ │
   ├──────────────────┬───────────────────────────────────┬──────────────────┤
   │ 左侧：AI 指挥台   │ 中央：实时 3D / UI 视口（主舞台）   │ 右侧：上下文抽屉  │
   │ · 设计规范记忆条  │ · 顶部悬浮：点选/圈选/涂鸦/屏幕比例 │ · 未选中时收起    │
   │ · 计划与步骤卡片  │ · 画面内气泡：选中物体直接快捷提问   │ · 选中节点/资产   │
   │ · 结构化执行流    │ · 底部轻栏：关卡流切换/预算条/快照轴│   时展示参数面板  │
   │ · 底部多模态输入  │                                   │   与外部打开按钮  │
   └──────────────────┴───────────────────────────────────┴──────────────────┘
   ```
   - 保证中央 3D 视口在默认状态下占屏幕 **60% 以上面积**；右侧手动属性面板和底部调试台平时收起或半透明叠层，点选对象或切到调试时才滑出，不挤压视口。

2. **拒绝大段废话气泡：对话流全面「卡片化与可交互化」**
   - **计划卡片（Plan Card）**：AI 拆出的步骤显示为可勾选、可展开的步骤列表，标明预计改动的模块与生成预算，底部带 `[开始执行]` `[调整计划]` 按钮。
   - **工具执行流（Action Pill）**：不把 JSON 参数直接糊在聊天里。每条指令显示为紧凑的单行胶囊，例如：`✓ 创建节点 [巡逻兵_01] · 贴地 (12.0, 0.0, -4.5)`、`✓ 编译脚本 patrol.ts (24ms)`。点击胶囊直接**在 3D 视口高亮并聚焦该物体**，或展开查看/回滚该步详情。
   - **内联微调控件（Inline Tweak）**：AI 刚调完水体、灯光或材质参数时，直接在对话流里嵌一张迷你滑条/颜色卡片（复用 `FieldSchema` 控件），人不用去翻右侧面板就能顺手拖动微调。
   - **变更汇总卡片（Diff Summary）**：每轮结束底部固定一张精简卡片：`本轮新增 3 个节点 · 修改 1 个脚本 · 体检 0 错误 | [▶ 试玩验证] [↺ 回退本轮]`。

3. **多模态输入与「@ 引用 / 视口胶囊」**
   - **视口点选自动入框**：在 3D 视口或层级树里点中物体/圈中区域，输入框上方立刻出现蓝色引用胶囊（如 `@主角`、`@水面`、`@框选区域(4个物体)`），支持一键移除。
   - **`@` 与 `/` 快捷指令**：输入 `@` 秒搜工程内的节点、资产、脚本、数据表、已安装能力包；输入 `/` 快速触发高频动作（`/playtest 跑冒烟`、`/diagnose 体检`、`/pack 沉淀为包`、`/checkpoint 打快照`）。
   - **剪贴板与拖拽直通**：直接 `Ctrl+V` 贴参考图、把资产库里的模型/贴图拖进输入框，自动转为多模态引用。

4. **AI 执行期的「视口实况反馈」（不让人对着转圈干等）**
   - AI 正在操作某个节点时，3D 视口里该物体出现柔和的脉冲描边与浮动小标签（如 `AI 正在编写巡逻脚本...`）。
   - 涉及其它资产编译或第三方生成任务时，视口角落显示非阻塞的进度条，人可以继续转视角观察场景，不被全屏遮罩锁死。
   - 顶部/输入框旁常驻醒目的 `[■ 停止 (Esc)]`，按一下立即在当前指令完成后安全停下，并提供 `[保留已完成步骤]` 或 `[整轮回滚]`。

5. **视觉与操控细节（专业工具质感）**
   - **深色高对比度工业风**：与 T3D 现有暗色面板语言完全统一，紧凑字号、等宽数字对齐、清晰的成功/警告/错误语义色，杜绝浮夸的大圆角大留白网页风。
   - **全键盘流支持**：`Cmd/Ctrl + K` 在视口内唤起就地指令框（对着当前选中物体直接下指令）；`Cmd/Ctrl + Enter` 确认计划/发送；`Space` 快速切换试玩与暂停。

### 8.2 内置 Agent 与模型接入

Agent 循环是 T3D 自己实现的：把对话、工程摘要、工具说明交给模型，执行模型要求的工具调用，把结果交回，直到这一轮结束。

```ts
interface ModelProvider {
  id: string                               // 'openai' | 'anthropic' | 'gemini' | 'openai-compatible' | ...
  models(): Promise<ModelInfo[]>           // 名称、上下文长度、是否支持工具调用与图片输入
  chat(request: ChatRequest, onDelta: (delta: ChatDelta) => void, signal: AbortSignal): Promise<ChatResult>
}

interface ChatRequest {
  model: string
  system: string
  messages: ChatMessage[]                  // 文本、图片、工具调用、工具结果
  tools: ToolSpec[]                        // 由工具面生成：名称、说明、参数（来自 FieldSchema）
}
```

- **可接各家 API。** 首批内置四个适配器：`openai-compatible`（通用兼容接口，填地址和密钥即可接 DeepSeek、通义千问、本地模型或各类中转服务），以及 `anthropic`、`openai`、`gemini` 三家原生适配器（以完整支持各自的流式工具调用、缓存和识图能力）。
- **请求从主进程发出。** 密钥存主进程（系统密钥库），渲染进程拿不到。流式结果经 IPC 回到界面。
- **设置里选模型。** 可以分别指定：规划用的模型、执行用的模型、看截图用的模型。不支持工具调用的模型不能用于执行。
- **工具说明自动生成。** 工具面把指令和查询的 `FieldSchema` 转成各家要求的参数格式，不手写第二份。
- **上下文管理。** 固定带系统说明和工程摘要；工具结果过长时截断并提示用查询工具取细节；对话过长时压缩早期内容，保留计划、已做的决定和未完成的事项。
- **可中断。** 任何时候可以停止；正在执行的指令做完当前这一条后停下，事务保持可撤销。
- **用量可见。** 每轮显示所用模型和消耗；可设单轮上限，超过时停下询问。

### 8.3 工作流程

1. **理解与立项记忆**：把需求整理并更新进工程的 `design.md`（类型、视角、核心循环、胜负条件、美术风格词、操作映射、关卡列表）。有歧义时提问。后续所有轮次自动携带 `design.md`，保证第 20 轮对话仍记得第 1 轮定的全局风格与规则。
2. **计划**：选最接近的配方，列出要开的包、要建的场景与物体、要生成的素材（连同预计调用次数和费用预估）、要配的策划表与组件、要写的脚本。**用户随计划一次确认**；执行过程中只要生成调用未超出计划预算，不再逐个弹窗打断。
3. **执行**：按步骤调指令。每步是一个子事务。出错按返回的 `hint` 重试，连续失败则停下汇报。
4. **验证**：体检 → 冒烟试玩 → 看截图。不通过回到第 3 步。
5. **交付**：汇报做了什么、验证结果、已知不足。询问是否导出、是否沉淀。

AI 模式的界面上显示计划清单与当前步骤，可暂停、可单步撤销、可整轮撤销。

### 8.4 配方

配方是一串带参数的指令，取代原计划里写死的脚手架。

```ts
interface Recipe {
  id: string
  title: string
  params: FieldSchema                      // 例如：地图大小、敌人数量
  requires: { capabilities: string[], packs: string[] }
  steps: Array<{ command: string, params: unknown, as?: string }>   // as：给结果起名，后面的步骤引用
  smoke?: string                           // 冒烟脚本资产
}
```

- 首批三个：平台跳跃、第三人称动作、俯视角射击。
- 人可以直接从菜单用配方（即原来的脚手架）。
- 配方可以随包分发（见第 10 节）。

> 注意区分两个概念：本节的「配方」是随包分发的 `PackRecipe`（`src/core/packs/`）；AI 用 `kb__read` 读取的「范例 / 技能 / 知识」是另一套可读可改的参考文本与源码，以及工程级规则与需求文档，统一见 `docs/ai-extensibility-design.md`。

### 8.5 生成能力模块

第三方生成服务封装成 T3D 的模块，AI 和人都能调。

```ts
interface GeneratorProvider {
  id: string                               // 'image.xxx'
  kind: 'image' | 'model' | 'animation' | 'ui' | 'audio'
  params: FieldSchema
  estimate?: (params: unknown) => { cost?: number, seconds?: number }
  submit: (params: unknown) => Promise<JobId>
```

- **任务队列**在主进程：提交、进度、取消、失败重试。结果一律是资产 ID。

- **生成界面**的产物是 `UiDocument` 加图片资产，不是 HTML。
- 每个生成的资产记录来源：服务、提示词、参数、时间、费用、许可说明。沉淀和导出时带上。

## 9. 便于 AI 生成的资源定义

AI 模式的产出质量，取决于每种资源「AI 好不好写、写错了能不能马上知道」。这一节定各类资源的形态，以及为此要补的基础能力。

### 9.1 四条标准

一种资源要适合 AI 生成，需要同时满足：

1. **是文本。** 一个资源一个文本文件，带稳定的 ID，可以整体重写，也可以局部修改，可以比较差异。
2. **能声明就不写代码。** 优先级：数据 > 公式 > 受限的代码模块。越靠前，AI 越不容易写错，也越容易检查。
3. **参数自描述。** 每个参数有类型、范围、默认值和一句说明，机器可读。AI 靠它知道能填什么，属性面板靠它自动生成。
4. **不运行游戏就能检查。** 能编译、能校验、能出预览图；出错时给出位置和原因，AI 可以据此自己改。

按这四条看现状：

| 资源 | 现状 | 评价 | 要做的事 |
|---|---|---|---|
| 界面文档 | 6 种节点的数据文档 | 好 | 补几种常用控件（9.6） |
| 数据表 | 表定义加行 | 好 | 无 |
| 预制体、场景 | 节点数据 | 好 | 走指令层即可 |
| 材质 | 5 个固定的 `SurfaceShader` 选项加 PBR 槽位 | 一般 | 改成「选一个着色器资产 + 参数表」（9.2） |
| 特效 | `simulation: unknown` | 差 | 参数化预设（9.5） |
| 着色器 | 不是资产 | 没有 | 新增（9.2） |
| 脚本 | 不是资产 | 没有 | 新增，作为 AI 写游戏逻辑的唯一代码方式（9.3） |
| 律令 | 面向手配的低代码步骤表 | 不用于 AI | 保留给开发模式手配，不进 AI 工具面（9.4） |

### 9.2 着色器资产

资产种类 `shader`，文件 `<工程>/shaders/<名字>.shader.ts`。

**AI 只写「表面长什么样」，不写「材质怎么建」。** 一个着色器资产是一个 TSL 模块，导出参数说明和一个 `surface` 函数；函数返回表面的各项输出：

```ts
import { defineShader, color, mix, sin, texture } from 't3d/shader'

export default defineShader({
  name: '流动岩浆',
  mode: 'lit',     // 'lit'（默认，走 PBR 受光）| 'unlit'（不受光，用于特效/全息/自发光材质）
  params: {
    baseMap:   { type: 'texture', label: '底色贴图' },
    glowColor: { type: 'color', default: '#ff5a1e', label: '发光颜色' },
    flowSpeed: { type: 'number', default: 0.3, min: 0, max: 2, label: '流动速度' },
  },
  surface({ params, uv, time, positionWorld }) {
    const flowUv = uv.add(time.mul(params.flowSpeed))
    const base = texture(params.baseMap, flowUv)
    const pulse = sin(time.mul(2)).mul(0.5).add(0.5)
    return {
      baseColor: base.rgb,
      emissive: mix(color(0, 0, 0), params.glowColor, pulse),
      roughness: 0.8,
    }
  },
})
```

- **两种光照模式：** `mode: 'lit' | 'unlit'`（默认 `'lit'`）。`'lit'` 走标准 PBR 光照与阴影；`'unlit'` 不受场景灯光影响，直接输出颜色与透明度，适合全息、能量盾、特效面片等材质。
- **可返回的输出：** `baseColor`、`normal`、`roughness`、`metalness`、`emissive`、`opacity`、`vertexOffset`。没返回的用默认值；返回值可以直接写普通数字/颜色或 TSL `Node`，由 `defineShader` 自动包装。
- **`params` 在 `surface` 里的类型：** 数值、颜色、向量类的 `params.xxx` 传入时已经是绑定好的 TSL uniform `Node`（可直接参与节点运算）；`texture` 类型的 `params.xxx` 是贴图对象，传给 `texture(params.xxx, uv)` 采样。
- **T3D 负责的部分：** 创建 `NodeMaterial`（`MeshStandardNodeMaterial` 或 `MeshBasicNodeMaterial`）、透明与混合方式、深度写入、双面、阴影、雾、后期需要的 MRT 输出。这些是材质上的选项，不在着色器代码里。这样 AI 写不坏渲染管线，`architecture-rules.md` 里的 MRT 保护规则由 T3D 统一保证。
- **不做着色器节点连线编辑器。** 着色器的唯一资产形态是 `.shader.ts` 文本代码；开发模式提供「实时材质球预览 + 自动生成的参数面板 + 轻量代码框 / 一键用外部编辑器打开 + 一句话让 AI 修改」，不维护第二套节点图 JSON。
- **参数：** 自动成为 uniform，自动出现在属性面板。材质资产的数据是「着色器 ID + 参数值」。
- **内置变量：** `uv`、`time`、`positionWorld`、`normalWorld`、`viewDirection`、顶点色等，由 T3D 提供，清单固定并写进文档。
- **只用 TSL。** 只能从 `t3d/shader` 引入（它转出一份经过筛选的 `three/tsl` 函数）。不接受 GLSL/WGSL 字符串。
- **现有 5 个固定着色器**（`lit`、`unity-standard`、`unlit-color`、`unlit-texture`、`particle-unlit`）改写成内置着色器资产。旧工程的材质数据自动迁移。
- **着色器模块也是会执行的代码。** 保存时做类型检查、引入来源检查和禁用的全局对象检查；从别处导入的包，启用其中的着色器前和脚本一样需要信任确认。
- **完整效果不在这一层。** 水体这类需要顶点动画、多遍采样、自带会话逻辑的效果，仍然是能力包。让 AI 写完整效果是更晚、更难的一档，本规划不排期。

**模型对 TSL 不熟**是已知问题，用三样东西缓解：一份允许使用的函数清单（带签名和一行说明）、一组官方示例、「类型检查/试编译失败 → 把错误交还 AI → 重写」的循环。

### 9.3 脚本资产

资产种类 `script`，文件 `<工程>/scripts/<名字>.ts`。语言是 TypeScript，一个文件一个模块。

**AI 写游戏逻辑统一用「已有玩法包组件 + TypeScript 脚本」。** 能靠配已有组件（角色、机关、属性、背包等）解决的直接配组件；需要自定义行为或流程时写脚本。

两种形状，对应两种用途：

| 形状 | 用途 | 入口 |
|---|---|---|
| 行为组件 | 挂在节点上的行为与事件响应（含碰撞、交互、消息、逐帧更新） | `defineBehavior` |
| 运行时系统 | 效果包或全局玩法用，接入帧流水线 | `defineSystem` |

```ts
import { defineBehavior } from 't3d/runtime'

export default defineBehavior({
  name: '巡逻',
  params: {
    speed:  { type: 'number', default: 2, min: 0, max: 20, label: '速度' },
    points: { type: 'list', item: { type: 'ref', target: 'node', label: '巡逻点' }, label: '巡逻路径' },
  },
  onStart(self) {
    self.state.index = 0
  },
  onStep(self, dt) {
    const target = self.params.points[self.state.index]
    if (!target) return
    if (self.moveToward(target.position, self.params.speed * dt)) {
      self.state.index = (self.state.index + 1) % self.params.points.length
    }
  },
  onMessage(self, message) {
    if (message.name === 'alarm') self.state.index = 0
  },
})
```

- **`ScriptApi` 的覆盖面**（脚本只能调用这些公开接口，不能访问 DOM、网络、文件、编辑器 store）：
  - **节点与空间**：读写位置/旋转/缩放、`moveToward` / `lookAt`、按标签或半径查找节点、生成预制体实例与销毁节点。
  - **脚本与组件通信**：发消息（`sendMessage` / 全局广播）+ 按类型获取目标节点上的其它脚本或玩法包组件实例（如命中敌人时直接读取或调用对方生命组件的方法）。
  - **物理与寻路**：射线检测与球体检测、施加力/冲量/速度、触发器与碰撞回调（`onTriggerEnter` / `onCollision`）、导航网格寻路移动（`navMoveTo`）。
  - **表现与输入**：播放动画片段、播放音效与粒子特效、读取 `input.json` 定义的语义化动作输入（如 `input.isPressed('Jump')`、`input.axis('Move')`，自动兼容键鼠/手柄/触屏虚拟摇杆）。
  - **界面交互**：读写界面绑定变量，监听界面控件发出的事件（如按钮点击、输入变化）。
  - **跨场景与存档**：切换场景（切关、回主菜单）、跨场景保留的全局运行时状态、本地存档读写（`storage.get` / `storage.set`）。
- **类型定义文件就是 AI 的手册。** `t3d/runtime` 的 `.d.ts` 由运行时公开接口自动生成，带注释，连同示例一起提供给 AI。大模型写受类型约束的 TypeScript 比拼装私有低代码 JSON 可靠得多，查错也直接靠编译器。
- **保存前做类型检查。** 检查不过不落盘成可用资产；错误带文件、行号、原因。
- **状态放在 `self.state`，不放模块级变量。** 这样才能热重载、存档、同一脚本挂多个实例。
- **遵守现有红线：** 试玩时不写 `useEditorStore.nodes`；不自己开 `requestAnimationFrame`；第三方库不进脚本；运行时系统只能通过 `registerRuntimeSystem` / `registerPhysicsExtension` / `registerBeforeRenderHook` 接入。
- **数据挂载位置：**
  - 当前工程里直接写的行为脚本，挂在节点上时数据存在保留包名 `node.gameplay.packs.__project__[scriptId]`（不新增 `SceneNode` 顶层字段）。
  - 沉淀进玩法包后，迁到该包的 `node.gameplay.packs[packId][componentId]`。

脚本的允许范围是规则变更，见第 12 节第 1 项。

### 9.4 律令的定位

律令（`RuleEntry` / `RuleStep`）是给人在开发模式里手配简单逻辑用的低代码模块，**不放进 AI 工具面**：

- 大模型本身擅长写带类型检查的 TypeScript，不擅长填自定义字段袋式的低代码 JSON；把律令暴露给 AI 反而要维护两套逻辑表达。
- 开发模式里的律令面板、现有律令运行时完全保留，不影响人手配，也不影响旧工程。
- `node.inspect` 如果读到节点上有人手配的律令，只返回一句只读摘要供 AI 知晓（避免 AI 误删或写出冲突脚本），AI 自己不增删改律令。

### 9.5 特效

`simulation` 现在没有类型。先不让 AI 直接写模拟数据，改为**参数化预设**：爆炸、火焰、烟、拖尾、火花、光环、命中等，每个预设一份参数说明（颜色、大小、数量、时长、速度等）。AI 选预设、填参数。预设不够用时由人在特效编辑器里做，再沉淀成新的预设。

### 9.6 界面文档

界面文档已经是适合 AI 的数据格式。常见游戏界面还需要的控件：按数据重复的列表、滚动区域、输入框、滑条、九宫格图片。开工前先核对现有 6 种节点和各玩法包里是否已有等价实现，缺的再补。

### 9.7 统一的参数说明

着色器参数、脚本参数、组件字段、指令参数、特效预设参数，**都用 4.2 的 `FieldSchema`，只有这一套。** 好处：

- AI 只需要学一种写法。
- 属性面板、校验、默认值填充、迁移只实现一次。
- 沉淀时「把写死的数值提成参数」对所有资源是同一个操作。

### 9.8 基础能力

为上面这些要补的底层工作，按依赖顺序：

| # | 能力 | 内容 | 依赖 |
|---|---|---|---|
| 1 | 统一的参数说明 | `FieldSchema`、校验、自动属性卡片 | 无（即 4.2） |
| 2 | 工程文件夹结构与独立代码文件 | 工程从新建起就是拆分好的磁盘文件夹（3.2 的目录结构），自动写出 `.t3d/runtime.d.ts`、`.t3d/shader.d.ts` 与 `tsconfig.json`。着色器和脚本作为独立 `.ts` 文件存放；内置轻量代码框 + 一键调起外部编辑器（Cursor / VS Code），文件监视器监听外部保存并自动同步 | 无 |
| 3 | 应用内编译、检查与模块加载 | 常驻工作线程跑 TypeScript 类型检查与转译（脚本和着色器都做类型检查）；将 `import ... from 't3d/runtime'` 与 `'t3d/shader'` 改写为运行时注入对象后加载执行；着色器另外复用主渲染器在离屏目标上试编译。所有错误统一成一种诊断格式：文件、行、原因、修改提示。播放包导出时将用到的脚本和着色器一起打入产物 | 2 |
| 4 | 运行时公开接口与类型定义 | `ScriptApi`；自动生成 `t3d/runtime` 与 `t3d/shader` 的 `.d.ts` | 运行时解耦（第 6 节） |
| 5 | 离屏预览（复用主渲染器） | 复用主视口同一个 `WebGPURenderer` 在离屏目标上渲染单张图：材质球、预制体、界面文档、特效某一帧（严格遵守单一渲染器红线，不建第二个渲染器）。用途三个：资产缩略图、AI 看图自查、包的展示图 | 试玩探针截图底座 |
| 6 | 热重载 | 着色器和脚本保存后立即生效，不重开试玩；脚本状态靠 `self.state` 保留 | 2、3 |
| 7 | 示例库与自动文档 | 每种资源一组官方示例；由登记表和类型定义自动生成的说明文档。两者都是给 AI 的上下文 | 1、4 |

另有一项针对具体资源的工作：特效参数化预设（9.5）。

**先后次序：** 先做第 1 项和运行时解耦、试玩探针；接着落代码类资产底座（第 2、3、6 项）和着色器资产；紧接着落脚本资产（第 4、7 项），这样进入 AI 模式时 AI 已经能写脚本和着色器。

AI 生成一个代码类资产的标准循环：

```
写文件 → 类型检查与试编译（第 3 项）→ 有错则按诊断修改，重复
       → 离屏预览或试玩验证（第 5 项 / 第 7 节）→ 不对则修改，重复
       → 落盘为资产，登记，可被材质或节点引用
```

## 10. 能力沉淀

**目标：每次创作结束，都能把这次做出来的东西提取成包，下次直接用。** 做完一个 RTS，可以让 AI 把其中的脚本、着色器、预制体、界面、数据表、配方整理成一个「RTS 包」。

### 10.1 包的三个层级

| 层级 | 内容 | 是否含代码 | 依赖的阶段 |
|---|---|---|---|
| 内容包 | 模型、贴图、材质、表面着色器、预制体、特效、界面文档、音频、数据表行、配方 | 只有表面着色器 | 阶段 4 |
| 玩法包 | 上面全部，加数据表定义、组件定义（字段说明 + 绑定的行为脚本） | 是（脚本） | 阶段 4 |
| 效果包 | 挂在帧流水线上的运行时脚本、场景或节点级能力，以及它们用到的着色器 | 是（脚本与着色器） | 阶段 4 |

三者共用一种包格式，只是内容不同。因为着色器与脚本资产在阶段 3 都已就绪，阶段 4 可以一次支持全部三种层级的包。

### 10.2 包格式

一个包是一个目录（分发时打成单个压缩文件）：

```
my-rts@1.2.0/
  pack.json              清单
  assets/                资产文件与元数据，按内容哈希命名
  prefabs/  ui/  materials/  effects/
  tables/                表定义与默认行
  components/            组件定义（字段说明 + 默认值 + 绑定的行为脚本）
  scripts/               行为脚本、运行时脚本
  shaders/               着色器资产
  recipes/               配方与冒烟脚本
  README.md              给人和 AI 看的说明
```

```ts
interface PackManifest {
  id: string                    // 'user.my-rts'，命名空间避免和官方包冲突
  version: string               // 语义化版本
  name: string
  description: string
  tier: 'content' | 'gameplay' | 'effect'
  engine: string                // 兼容的 T3D 版本范围
  dependencies: Array<{ id: string, version: string }>   // 官方或其它用户包
  provides: {
    tables?: string[]; components?: string[]; scripts?: string[]
    shaders?: string[]; capabilities?: string[]; recipes?: string[]
  }
  provenance: { sourceProject?: string, createdBy: 'user' | 'ai', createdAt: string, licenses: LicenseNote[] }
  trust: 'local' | 'imported'   // 导入的包首次启用脚本或着色器前需要确认
}
```

### 10.3 让登记表能在运行期加包

现在两个登记表是编译期常量。需要改成「官方包 + 已安装的包」：

- `registerGameplayPack` 和能力登记都接受运行期登记与注销。
- 用户包的组件**不带 React 卡片**，属性卡片由字段说明自动生成（4.2 的产物），行为由绑定的脚本实现。官方包保留手写卡片。
- 数据仍然放在既有挂载槽：`node.gameplay.packs[packId][componentId]`、`node.capabilities[id]`、`picture.capabilities[id]`。不新增顶层字段。
- 工程里记录用到的包与版本。**工程自带一份包的副本**（`<工程>/packs/`），保证换台电脑能打开、能导出。

### 10.4 脚本与着色器进包的前提

沉淀「脚本包、着色器包」的前提是它们先成为资产，定义见 9.2 和 9.3（在阶段 3 落地）。沉淀时，工程内挂在 `node.gameplay.packs.__project__[scriptId]` 的脚本组件自动规整到新包的 `packId` 下。

### 10.5 沉淀流程

入口：菜单「沉淀为包」，或对 AI 说「把这个工程的 RTS 部分做成包」。

1. **圈定范围。** 用户或 AI 选起点：某些预制体、某些脚本与组件、某个界面、某组数据表，或「整个玩法」。
2. **依赖闭包。** 从起点沿引用关系收集：资产、材质、贴图、片段、数据行、界面文档、脚本、着色器、组件。列出清单给用户看，标明哪些来自官方包（只记依赖，不打进包）。
3. **泛化。** 这是沉淀和「复制粘贴」的区别，主要由 AI 完成、用户确认：
   - 把工程特有的引用换成**插槽**（例如「主基地模型」），安装时由使用者填或用默认值。
   - 把写死的数值提成**参数**（字段说明），放进组件定义或配方。
   - 把只在这一关用的内容（具体关卡布局、剧情文本）剔除或挪进示例场景。
   - 命名规整，加命名空间。
4. **生成配方与说明。** 把「怎么用这个包搭出一个可玩的最小例子」写成配方，附一份冒烟脚本和 README。
5. **干净环境验证。** 新建空工程 → 安装这个包 → 跑配方 → 体检 → 冒烟试玩。**不通过不能发布。** 这一步保证包不暗中依赖原工程。
6. **发布。** 写入用户库，记录版本、来源工程、许可说明。库窗口里出现在对应栏目。

### 10.6 安装、版本与冲突

- **用户库**：`<用户数据目录>/T3D/library/packs/<id>@<version>/`。库窗口四栏不变（能力、玩法、专项、素材），用户包按 `tier` 归栏并标「我的」。
- **安装到工程**：复制到 `<工程>/packs/`，登记，资产按哈希去重。
- **版本**：同一个包再次沉淀时升版本。数据结构变了要带迁移函数（旧数据 → 新数据），否则只能作为新包。
- **冲突**：包 ID 带命名空间；词条和表 ID 自动加包前缀；资产按内容哈希，同内容不重复。
- **卸载**：与关闭官方包一致。数据保留，标缺失，不静默运行。
- **导出**：播放包只带用到的包内容。
- **来源与许可**：包内每个资产保留来源记录。含第三方生成或导入素材时，发布前列出许可提示。

### 10.7 沉淀如何反哺 AI

- `registry.describe` 把已安装的用户包和官方包一视同仁地暴露给 AI。
- AI 做计划时先查库：有合适的包和配方就直接用，没有再从头生成。
- 每个包的 README 和配方就是 AI 的使用说明。**包越多，AI 生成的质量和速度越高。**

## 11. 阶段规划（5 阶段主线，六大管理支柱按序就位）

既然生产以 AI 为核心、T3D 定位为六大支柱的游戏工程管理器，**内置 Agent、工程文件树、`design.md` 全局设计记忆和轮次快照从阶段 1 起就全部就位**；后面每个阶段依次把「试玩调试与多端适配 → 代码资产与外部工具链桥接 → 完整六大管理视图、快照分支与能力沉淀 → 第三方素材生成与自动入库守门」叠加上去：

### 阶段 0 · 接口契约、工程目录与规则修订

在动工写代码前，先把代码类资产的接口契约和拆分后的工程文件夹结构定死，避免后面返工。

- 定好 3.2 的工程文件夹拆分结构（`project.json` + `design.md` + `input.json` + `scenes/` + `prefabs/` + `ui/` + `materials/` + `tables/` + `scripts/` + `shaders/`）。
- 写出 `t3d/shader.d.ts` 与 `t3d/runtime.d.ts` 初稿（含 `defineShader`、`defineBehavior`、`defineSystem`、`ScriptApi` 全部签名，输入接口采用语义化动作名）。
- 用这两份类型文件试写 3 个着色器（如流动岩浆、全息、卡通）和 3 个脚本（如巡逻、移动平台、射击/扣血），跑通类型检查，确认接口无缺口。
- 按第 12 节修订 `architecture-rules.md` 和 `.cursor/rules/`（工程管理器六大支柱定位、脚本边界、着色器资产、不做节点连线图、指令层红线）。

完成标志：两份 `.d.ts` 与 6 个样例通过类型检查；工程目录格式与规则文档定稿。

### 阶段 1 · 指令层、设计中枢、基础快照与内置 Agent（AI 最早可用）

第一步就落好「支柱 1：立项与设计中枢」和「支柱 5：基础轮次快照」，让 AI 住进编辑器，能带着 `design.md` 全局记忆搭场景、改策划表、配现有组件。

- 工程文件夹读写、`design.md` 全局设计记忆维护、每轮自动文件快照（Checkpoint）与一键回退；文件接口加路径校验。
- 指令总线、事务、结构化错误；试玩期间拒绝文档修改指令。
- 首批 7 个指令域（`scene`、`capability`、`gameplay`、`ui`、`asset`、`picture`、`project`），含贴地/对齐放置与 `design.md` / `input.json` 读写。
- `FieldSchema` 与自动生成属性卡片；先迁移水体、物理、角色、机关、属性包作为样板。
- 查询工具（含包围盒尺寸、原点信息、数据表引用统计）与 `project.diagnose` 基础体检。
- **内置 Agent 核心与专业对话面板**：模型接入与首批 4 个适配器（`openai-compatible` + `anthropic` / `openai` / `gemini`）、主进程发请求与密钥存储、工具说明自动生成、Agent 循环（自动注入 `design.md`）；左侧停靠式 AI 指挥台从第一版起即采用**结构化卡片设计**（计划确认卡、可点击聚焦视口的指令执行胶囊、`@` 节点/资产引用胶囊、`Esc` 安全中断，见 8.1a）。

完成标志：在编辑器里用一句话立项，AI 先生成 `design.md` 设计概要，再从空工程搭出平台跳跃关卡（地面、主角、平台、检查点、水体、已有玩法包组件、策划表、界面），体检无错误，可一键回退到任意一轮快照。

### 阶段 2 · 运行时独立、多端试玩台、调试预算与 Web 导出（打通试玩、调试与发布）

落好「支柱 3：实时试玩台」「支柱 4：调试、体检与性能守门」和「支柱 6：基础 Web 导出」，让 AI 产出的工程能多端预览、能被自动试玩和性能守门、能独立导出。

- `RuntimeWorld` 接口；运行时与能力、玩法的会话代码不再引用编辑器；界面文件迁出 `src/runtime`。
- `input.json` 语义化动作输入映射落地（键鼠/手柄/触屏虚拟摇杆统一映射）；试玩台支持桌面横屏、移动竖屏/横屏比例切换。
- `PlaytestSession` 试玩探针：定步长推进、虚拟输入、状态读取与断言、截图、帧耗时与报错报告。
- 性能预算守门（面数、DrawCall、显存、包体大小实时监控，超标进 `project.diagnose` 体检报警）。
- 复用主渲染器的离屏预览（9.8 第 5 项）：预制体、界面文档、场景截图。
- 冒烟脚本资产与执行器；现有玩法测试迁到探针上。
- Web 播放包入口、导出流程、依赖检查；探针与导出接入 Agent 工具面。

完成标志：AI 搭完关卡后自己启动试玩探针跑冒烟、看截图与性能预算自检并修复问题，支持切换手机/桌面比例试玩，最后一键导出可在浏览器独立运行的 Web 播放包。

### 阶段 3 · 脚本资产、着色器资产与外部工具链桥接（AI 获得完整代码生产能力）

把脚本和着色器交给 AI，并打通外部编辑器/DCC 工具的双向热重载桥接。

- 代码类资产作为独立 `.ts` 文件管理；内置轻量代码框 + **外部工具链桥接**（一键用 Cursor / VS Code / Blender / PS 打开代码或资产，文件监视器监听外部保存并自动热重载）。
- 常驻工作线程跑 TypeScript 类型检查与转译；`t3d/runtime` 与 `t3d/shader` 模块注入加载；复用主渲染器做着色器试编译；结构化诊断。
- `shader` 资产：`lit / unlit` 模式、参数说明、`surface` 函数、内置变量；现有 5 个固定着色器迁移为内置着色器资产；材质球离屏预览；官方示例库与 TSL 白名单。
- `script` 资产：`defineBehavior` 与 `defineSystem`、`ScriptApi` 落地（含语义化输入、物理寻路、跨场景与存档）、`self.state`、热重载、单脚本帧耗时统计、`__project__` 挂载槽；官方示例库。
- 特效参数化预设与界面控件补充（9.5、9.6）。
- AI 的代码生成闭环：写文件 → 类型检查/试编译 → 按诊断修改 → 预览或试玩验证 → 落盘。

完成标志：让 AI 做一个含多场景流转（主菜单 → 关卡 → 结算）、自定义行为脚本（巡逻、射击扣血、存档）和自定义表面着色器的完整小游戏；在外部 Cursor 修改脚本或着色器保存后视口直接热重载生效；试玩通过并可导出。

### 阶段 4 · 六大管理视图工作台、快照分支与全层级能力沉淀

把工作台界面完整升级为「AI 指挥台 + 六大工程管理支柱 + 手动辅助抽屉」，并打通全层级能力沉淀。

完成标志：通过「立项蓝图 + 对话 + 视口圈选指点 + 分支对比」完成一个小型 RTS 工程，将它一键沉淀为「RTS 能力包」；新建空工程安装该包，AI 直接调用它和它的配方搭出新关卡并试玩通过。

## 12. 关键设计决策汇总

以下事项已完成确认，阶段 0 直接按此落入规则与类型定义：

0. **工具总定位与六大支柱（已定）。** 生产过程以 AI 为核心；T3D 定位为「AI 驱动的游戏工程管理器」，承担六大职能：立项与设计中枢（`design.md` 与关卡流图）、资源/策划表与包管理（含资产入库自动规整与外部工具链桥接）、多端实时试玩台（含 `input.json` 语义化输入映射）、调试/体检与性能预算守门、版本快照与实验分支对比、验证发布与能力沉淀；手动编辑退居为局部微调的辅助手段，不再新建重型手配工作台（第 1、8.1 节）。
1. **脚本的边界与逻辑分工（已定）。** 放宽为两种形状（`defineBehavior` 行为组件、`defineSystem` 运行时系统），限定在 `ScriptApi` 内；AI 写游戏逻辑统一用「已有玩法包组件 + TypeScript 脚本」，律令只留作手动辅助（9.4）。
2. **脚本间的通信与 `ScriptApi` 范围（已定）。** 支持消息广播 + 按类型获取目标节点上的其它脚本/组件实例；第一版 `ScriptApi` 涵盖空间移动、物理射线/施力/碰撞回调、导航寻路、动画/音效、UI 变量读写与事件监听、跨场景切换与全局状态、本地存档读写（9.3）。
3. **着色器的形态与光照模式（已定）。** AI 与用户只写表面输出，只用 TSL，支持 `lit`（PBR 受光）和 `unlit`（不受光）两种模式；不做着色器节点连线编辑器，采用「实时材质球预览 + 自动参数面板 + 轻量代码框/外部编辑器 + AI 修改」；水体这类完整效果仍是能力包（9.2）。
4. **工程存储与外部工具链桥接（已定）。** 工程从新建起就是按职责拆分的磁盘文件夹（`project.json` + `design.md` + `input.json` + `scenes/` + `prefabs/` + `ui/` + `materials/` + `tables/` + `scripts/` + `shaders/` + `assets/` + `packs/`），自带 `.d.ts` 与每轮快照/实验分支；内置轻量代码查看/编辑框，支持一键调起外部工具（Cursor / VS Code / Blender / PS）并监听保存自动热重载（3.2、9.8）。
5. **AI 的入口与首批模型适配器（已定）。** 不用 MCP，不依赖外部 Agent；T3D 内置 Agent 并从阶段 1 起常驻；首批提供 `openai-compatible` 通用接口 + `anthropic`、`openai`、`gemini` 四个适配器（8.2）。
6. **打包与包分享范围（已定）。** 第一版只做 Web 播放包，不做桌面安装包；包管理只做本机用户库和文件导入导出，不做在线商店，导入含脚本或着色器的包需信任确认。

## 13. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 指令层改造面大 | 约 90 个动作加卡片里的直接修改 | 只迁 AI 需要的域；界面交互类不动；新旧并存，逐卡片迁移 |
| 运行时解耦动到核心文件 | 律令、角色、机关都引用了编辑器 store | 先加 `RuntimeWorld` 适配层再逐文件替换；靠玩法测试和探针兜底 |
| 脚本无法做到完全隔离 | 脚本和运行时在同一个线程里跑，才能进帧流水线 | 接口注入 + 静态检查 + 信任确认；不承诺对恶意代码的隔离；导入的包默认不启用脚本和着色器 |
| 脚本拖垮帧率或破坏红线 | AI 或用户写出每帧写 store、每帧重建对象的代码 | `ScriptApi` 不暴露 store；探针报告里统计每个脚本的帧耗时并在体检中报警 |
| 泛化质量 | 沉淀出的包暗中依赖原工程，或参数提得不合理 | 干净环境验证是硬门槛；泛化结果由用户确认 |
| 包版本与数据迁移 | 包升级后旧工程数据对不上 | 清单带版本与迁移函数；没有迁移函数时只允许并存不允许覆盖 |
| 生成素材的许可 | 第三方生成与导入素材的再分发 | 来源记录随资产走；沉淀与导出时列出提示 |
| 各家模型能力不一 | 工具调用的可靠性、上下文长度、是否能看图差别很大 | 适配器声明模型能力；不满足要求的模型不能选作执行；用同一组冒烟任务评测每个接入的模型 |
| 自研 Agent 的工作量 | 循环、上下文压缩、错误恢复都要自己做 | 阶段 1 先落最小可用 Agent 循环，在后续每个阶段持续用真实任务迭代 |
| 模型对 TSL 不熟 | TSL 资料少，模型容易写出不存在的函数或按 GLSL 的习惯写 | 只开放一份筛选过的函数清单；官方示例进上下文；类型检查与试编译失败自动把诊断交还重写；限定只写表面输出，缩小出错面 |
| 应用内检查的体积与耗时 | 脚本与着色器类型检查要把 TypeScript 编译器随应用分发，首次检查慢 | 放在常驻工作线程里跑；只检查改动的文件；试编译复用主渲染器，不额外建渲染器 |
| 材质改造影响旧工程 | 5 个固定着色器改成着色器资产，材质数据格式变化 | 带迁移；用现有工程做前后截图对比，外观不变才算通过 |
| 两种渲染后端结果不一致 | 同一个着色器在 WebGPU 和 WebGL2 回退下表现不同 | 日常保存用当前后端试编译；导出与发布包时可选跑双后端检查 |
| AI 生成质量受限于能力丰富度 | 模型再强，T3D 没有的能力也调不出来 | 配方和包优先；沉淀机制本身就是为了让能力持续增长 |

## 14. 与现有规则的关系

本规划不改变以下红线：单一渲染器、后期走 `RenderPipeline` + TSL、图层保留、试玩时不高频写 store、增量同步、蒙皮包围盒、节点种类互斥、不做积木系统、不做逻辑连线图主界面、数据挂载槽。

需要修订或新增的规则（阶段 0 完成）：

- 新增：**编辑器定位为 AI 驱动的游戏工程管理器**（资源与包管理、调试、试玩、发布），手动编辑作为局部微调辅助；停止新建重型手配工作台，新增能力一律只提供 `FieldSchema` + 指令/API + 运行时逻辑。
- 新增：工程数据的修改必须经过指令层；卡片组件不直接拼数据写 store。
- 新增：运行时代码不得引用 `src/editor/`。
- 新增：用户包与官方包走同一套登记；用户包数据同样只进既有挂载槽。
- 修订：脚本的允许范围（按第 12 节第 1、2 项）。
- 修订：「新增自定义着色器统一使用 `NodeMaterial` + TSL」补充一条：用户与 AI 编写的着色器走着色器资产（9.2），只写表面输出，材质由 T3D 创建。
- 新增：各类资源的参数说明只用 `FieldSchema` 一套（9.7）。
- 新增：工程统一为按职责拆分的磁盘文件夹结构（3.2）；着色器与脚本是工程目录下的独立文本文件，不内嵌进工程 JSON。
- **不做节点连线图主界面**的范围扩充：除脚本和动画状态机外，着色器同样不做节点连线编辑器（9.2）。
- 修订：「第一版不实现安装器」改为「实现本机包的安装与沉淀，不做在线商店」。
- 修订：「不做创作模式与高级模式的切换」改为「不做积木式的简化模式；AI 生产与手动辅助操作同一套工程文件，能力不分叉」。
- 新增：模型与生成服务的密钥只存主进程；网络请求只从主进程发出。
